## 目的と今回の終了点

[実装報告書の原因調査](39_completion-implementation-report.md)で残った不明点を、原要件・実装経路・実測証拠から絞り込む。**今回は追加調査と結果報告まで。修正実装計画は結果を評価した後に作成する。** 製品コードの修正・通常稼働への反映を先行しない。既存の[実装計画docs/38](38_completion-implementation-plan.md)は依頼正本として維持する。

「試験が未実施」と「機能が未実装／不具合」を区別し、どのファイルの何を直す必要があるか、または修正せず検証を追加すればよいかを判断できる情報を得る。先行報告の推測を結論として追認しない。

## 調査時の境界

- 読取調査から開始する。追加測定が必要なら、`work/sol-investigation-<日時>/`内の診断器・隔離コピーだけへ最小限の計測を追加し、元との差分とhashを記録する。計測追加による挙動変化も限界として記載する。
- 通常Slicerの仮C・カメラ姿勢・既存台帳を変更しない。確定・取消・シーン保存・移行をしない。通常プロセスを試験用として終了しない。
- 実機再現は既存の隔離fixture管理を使用し、合成非患者シーン・専用ポート・専用台帳で行う。試験Slicerは同時1個。所有PIDを照合し例外時も終了する。通常と試験の同時入力を避け、入力切替が必要なら既存の停止／lease解放／停止復帰経路を使う。
- 患者情報、CT/DICOM、カメラ画像、映像、音声を保存・外部送信しない。UI証跡は合成シーンのみとし、カメラプレビューを含めない。診断は時刻・状態・数値・接続先等の必要なメタデータに限定する。
- 証明書・信頼ストア・権限設定を変更しない。署名拒否を迂回しない。調査に必要な機能が現在の権限で使えなければ、その項目だけを未取得とする。
- 自作入力／期待値による試験は自己検証。実Slicer観測、実手、独立検収を分ける。過去FAILは保存し、再現なしを原因解消としない。
- 検索対象を先に限定し、JSON配列はツール内で集計する。全ログをそのまま出力しない。

## 追加調査項目

### I-01 状態鮮度17件の異常を切り分ける（優先1、W-04/07）

対象：`tools/observe_normal_connection.py`、`prototypes/cmos-motion-poc/ui_bridge.py`・`session_client.py`・`app.py`、先行`work/sol-normal-connection-600-20261011/results.json`と最終`work/sol-source-frozen-normal-600-20261011/results.json`。

取得する情報：

- 先行異常415.875〜419.079秒の前後を集計し、連続区間・状態値の反復・観測間隔・接続世代を確認。元時刻が欠ける箇所は復元不能とする。
- capture→推論→同期status→publish→読取の実際の呼出順、同一スレッドか、待ち／timeout／再接続の上限、例外処理をファイル・関数・行で示す。
- 追加診断が必要なら、発行側と読取側の単調時刻／壁時計、連番、生のage、status開始終了・timeout、Qt heartbeat、capture／推論終了時刻を取得。異なるプロセスの時刻を無補正で差し引かない。
- status応答遅延、capture遅延、推論遅延、Qt停止、時計変化、観測側停止を区別する。安全な隔離再現を選び、正常対照と比較する。各候補を「再現で支持／反証／未検証」に分類する。

終了条件：どこで更新が止まるかを証拠で特定、または候補を識別できない具体的な不足情報と最小の追加実験を記載。再試験PASSや多重Slicer残存だけから因果を断定しない。

### I-02 Qt遅延・編集遅延・順序逆転で本当に破綻するか（優先1、W-05/F-01）

対象：`tools/slicer_completion_bootstrap.py`、`tools/completion_fault_test.py`、`command_protocol.py`、`CStampModule.py`、`cstamp/contracts.py`と関連保存処理。

ACKを無効化する既存render-holdと、実Qt処理遅延の違いを整理する。受信→キュー→編集→描画→ACK→確定→保存の経路と版束縛点を図または表で示す。遅延編集が確定より後に実行される場合、古いACKが届く場合、確認中に版が変わる場合を調べる。

隔離再現ではreq、接続世代、draft ID、要求rev/hash、実行rev/hash、表示rev/hash、保存rev/hash、拒否理由、保存増分0／1を一組で残す。単一TCPのバイト順と、異なる処理・世代間の順序逆転を混同しない。

終了条件：不具合を再現した経路、保護されていた経路、まだ試験器がない経路を分離。試験不足だけで製品不具合と断定しない。

### I-03 手／マウス同等性と4喪失条件（優先1、W-06/AC-007）

対象：`hand_menu.py`、`op_controller.py`、Slicer Widget／dispatcher／入力所有権、`tools/observe_fixture_mouse.py`、マウス試験結果。

全操作を原文から列挙し、手入口→命令→共通処理と、実UI入口→命令→共通処理の対応・欠落を調べる。配置、表面移動、開口、傾き、反転、リセット、確認、確定、取消、停止／再開、計画・理由・監査操作を省略しない。

手無効・遮蔽・カメラ断・通信断の各条件で、明示マウス引継ぎ、古い手要求の失効、手復帰時の開始／解放条件を比較する。保存比較で除外する時刻・生成ID・入力手段は先に定義し、対象・幾何・状態遷移・版束縛・監査項目を除外しない。

UI操作は実画面の対象を確認して行う。表面連続ドラッグとslider値設定を別項目にする。実手が必要な条件は未実施と明記し、合成入力の代替範囲を示す。

終了条件：未接続／意味的な差／UI入力先の誤り／試験不足を操作別に分類し、各差に再現手順と証跡を付す。

### I-04 グー／親指と実手試験の準備不足（優先2、W-07）

認識分類→保持／解放→メニュー→送信→Slicer拒否理由までの切分け点を確認する。左右反転、手の左右判定、閾値、保持中の誤分類がどこへ作用するかを示す。既存画像由来入力は補助的な自己検証とする。

480試行表とH/V22ケースについて、記録機能があるか、手順表示と意図ラベル入力があるか、欠落・中断・再試行をどう残すかを確認する。不明形／遷移の空配列を「0件成功」と数えない。利用者の実手提示が必要なら、調査側の起動・表示・記録準備を先に整え、短い再現手順を提示する。

終了条件：現在の誤認識を実証できたか、未観測かを明記。全480試行の受入完了を今回の原因調査の条件にはせず、修正判断に必要な最小再現と残る本受入を分ける。

### I-05 旧計画データの復元可能範囲（優先2、W-03/F-05）

旧6行の原本hashを照合し、欠落項目を行／版ごとに表にする。`plan_diagnostics.py`・`plan_revision.py`の読込／保存要件と照合する。既存の当該計画に限定したバックアップ・保存記録に必要な値が残るかを調べる。別タスク・患者データへ探索を広げない。

終了条件：原記録で復元可能な値、欠落して復元不能な値、表示／導線上の問題を分離。復元不能ならそれを結論とし、値を創作した移行案を出さない。

### I-06 試験プロセス残存とUI誤入力（優先2、W-05/09）

既存起動・終了ツールの正常終了、起動失敗、ready前失敗、試験例外、中断のcleanup経路を確認。launcherと実Slicer PIDの対応、PID再利用対策、lock解除、起動経路による管理漏れを調べる。通常プロセスを終了しない。

UIのfocus不成立／座標drag誤入力を既存証跡で確認し、ウィンドウ重なり・座標依存・状態確認の不足を区別する。過去の全8プロセスの起動履歴を再構成できない場合、その限界を記載する。

終了条件：現行管理に残る穴と、既に対策があるが未検証の条件を区別する。

### I-07 通信・保存先・権限監査（優先2、W-08/X-08）

間欠TCP照会・UDPローカル端点・観測者トークンの証拠では何が未取得かを整理する。対象プロセスの実効権限、送信先、ファイル書込先を内容なしのメタデータで取得できる既存手段を調査する。採取期間・PID識別・欠落・必要権限・性能影響を示す。

可能な範囲で実測するが、権限昇格・通信遮断・信頼設定変更やペイロード収集は行わない。一般ユーザーでの対象全操作成立を観測者の非管理者判定から推定しない。

終了条件：現在取得できる証拠と、取得できない証拠・理由・必要な役割を明記する。

### I-08 署名後の配布経路と依存条件（優先2、W-08/F-09）

`prepare_completion_release.py`、`verify_completion_release.py`、起動／更新PS1と候補manifest／SBOMを確認。署名対象、署名後hash採取順、catalogの束縛、同梱依存、外部実行物、選択版起動、停止判定、rollback、失敗時pointer復帰を追跡する。

署名なしで読取確認できる実装不足と、正規署名が必要な試験を分離する。正規の署名手段・担当が既存文書に明記されているか確認し、未指定なら「未指定」とする。秘密鍵・証明書の新規作成／エクスポートや信頼ストア変更は禁止。

終了条件：署名を得れば何を実行できるか、署名以外にも不足があるかを具体化する。NotSigned拒否成功を配布成功にしない。

### I-09 証拠と報告の一致・未解消Fの粒度（優先2、W-09）

docs/39、docs/36、要求追跡CSV、`work/record_sol_completion_report.py`を対象に、未解消F-01〜09を原文条件へ分解し、証拠の版／経路／合否／未実施を対応付ける。マウス13チェックに対して本文12と記載された固定値の箇所、再生成で誤記や追記が失われる範囲を確認する。

終了条件：単なる件数一致と意味的な要求成立を分離し、修正候補を「製品コード／試験器／文書生成／運用手順／外部依存」に分類する。独立検収は別担当の実証がない限り未実施。

## 成果物と報告形式

- 結果報告：`docs/42_sol-additional-investigation-report.md`。調査してから作成し、未取得の結果を先に埋めない。
- 証跡：`work/sol-investigation-<日時>/`。入力条件・対象版・計測器差分・実測・失敗・終了状態を保存。既存証跡は参照で済ませ、変更しない。
- docs/39に結果報告へのリンクと判明事項を追記。`PROJECT_STATUS.md`に現在地・残る情報・次の判断を記録する。

各Iについて次の項目を必須とする。

| 項目 | 記載内容 |
|---|---|
| 原要求／対象版 | 原文の箇所、ソース・設定hash、実行環境 |
| 質問／仮説 | 何を区別するために調べたか |
| 手順・実行段階 | 読取／自己検証／実Slicer／実手を区別 |
| 実測事実 | 値、状態、件数、版、失敗、証跡パス |
| 原因判定 | 確定／支持する証拠あり／未特定。反証・代替原因も記載 |
| 修正要否 | 必要／不要（試験追加のみ等）／情報不足 |
| 修正候補箇所 | ファイル・関数・呼出経路。まだ修正を実装しない |
| 残る情報 | 取得方法・担当役割・進められない理由 |

## 修正実装計画へ進む条件

1. I-01〜09の全てに結果または具体的な未取得理由がある。
2. 修正対象にする不具合には再現証拠または原文との実装不一致がある。試験未実施だけを根拠に作り直さない。
3. 未特定原因を確定原因と書かず、計画には原因確定の追加計測を別工程として残せる。
4. 各修正候補に対象ファイル、期待する変化、回帰条件、通常仮C／台帳の保護方法を記載できる情報がある。
5. 結果を依頼元で評価してから修正実装計画MDを作る。調査中に製品修正・配布反映へ進まない。
