# Solution Brief: 非接触3D視点モーションコントローラー

## Problem Recap

取得済み心臓3Dモデルの表示視点を、指定された操作者が清潔域を維持したまま回転・パン・ズームできるかを非臨床環境で検証する。現状はカメラ入力と変換ロジックの断片的なPoCがある一方、要求から設計コンポーネントへの割当て、安全状態、出力許可条件が設計として固定されていない。

## Proposed Solution

標準PoCではPixel 9aを映像入力、Google MediaPipe Tasks Hand Landmarkerを手認識に使用する。Pixel 9aまたはUSBカメラは交換可能な映像入力として扱い、その観測を、認識・動作量変換・安全判定・出力に分離したフェイルクローズ型コントローラーへ渡す。起動時、認識不能時、複数人検出時、カメラ切断時、対象ウィンドウ不一致時は出力しない。既定はプレビューのみとし、実出力には起動時許可、手動アーミング、対象プロセス一致の全条件を必要とする。

PixelのWindows接続カメラ機能は映像取得手段としてだけ利用する。PixelのIMUや端末側モーション認識を制御経路へ直接転用する案は、通信断、認証、構成管理、外部依存の追加評価が必要な別方式として扱う。

## Key Features

1. **交換可能な映像入力:** DirectShowカメラを共通インターフェースで扱い、Pixel固有機能を制御ロジックへ混入させない。

2. **フェイルクローズ状態管理:** 無効、待機、追跡、実行、異常を明示し、条件喪失時は出力解放後に無効または異常へ遷移する。

3. **限定された視点操作:** 回転、パン、ズーム、基準視点復帰候補だけを型付き操作として扱い、任意キー・任意コマンドを生成しない。

4. **二重の出力ゲート:** 明示的な実入力許可と対象プロセス／ウィンドウ一致を満たす場合だけ、許可済みマウス操作を出力する。

5. **非映像の検証証跡:** 時刻、状態遷移、認識種別、動作量、抑止理由を記録し、カメラ映像、画面映像、患者情報は保存しない。

## Trade-offs Considered

| What We're Not Doing | Why |
|---------------------|-----|
| Pixel固有のIMU／モーションAPIを直接制御入力にする | カメラ方式とは別の通信・認証・切断リスクを追加し、現要求の「ローカルPCとカメラ」を逸脱するため |
| 認識結果からPyAutoGUIを直接呼ぶ | 状態管理、対象確認、解放処理を迂回でき、誤出力の原因になるため |
| 任意キー・任意アプリ操作 | 許可スコープ外であり、治療機器やOS操作への到達を防ぐため |
| 完成済み仮想マウスOSSの流用 | 多くが汎用PC操作を前提とし、許可操作とフェイルクローズ条件を保証しないため |

| 誤認識・複数人による出力 | 未評価 | 未評価 | 単一操作者条件、信頼度・安定時間、安全ゲート、曖昧時無入力 |
| カメラ／通信切断後の残留入力 | 未評価 | 未評価 | フレーム鮮度監視、即時ボタン解放、異常ラッチ、手動再アーミング |
| 対象外ウィンドウへの入力 | 未評価 | 未評価 | タイトル部分一致を廃止し、プロセスIDとウィンドウIDの許可リストで確認 |
| OSSの保守・通信挙動 | 未評価 | 未評価 | バージョン固定、SBOM、ライセンス確認、ネットワーク監査、認識アダプター分離 |
